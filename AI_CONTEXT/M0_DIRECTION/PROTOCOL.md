# M0 对话接力与第一层统筹协议 v7

## 1. 目的

让 M0 产品方向在以下环境间连续恢复：

- 当前 Mac 第一层总控：`M0-DIR-A`；
- Mac 上由第一层创建和收回的第二至第四层任务；
- 新建任务、不同 Codex/ChatGPT 项目外壳与不同终端。

协议不依赖聊天同步或云项目。当前不设计 Windows 路线；Windows 历史 session 只作为既有证据保留。任何新的 Mac 任务只要能读取同一 Git 仓库和 `context/m0-direction` 分支，就能恢复讨论。

## 2. 本聊天的职责边界

方向聊天只确认“做什么、为什么做、做到什么程度”。

允许：

- 产品定位、目标玩家与核心体验；
- 玩法闭环、情境顺序、决策和后果；
- 方案比较、收益、成本、风险与机会成本；
- M0 范围、非目标、成功、失败与恢复标准；
- 节奏、数值区间、盲测指标与 Go/No-Go；
- 只读检查现有文档或代码，以判断技术可行性；
- 形成可由第一层派发给其他层任务的冻结规格与实施任务包。

禁止：

- 修改游戏代码、数据、资产、产品规格或服务器；
- 运行会修改产品数据、生成需提交产物或改变外部状态的脚本、部署或发布；第四层交付后，第一层可以运行不改语义的独立测试、构建和浏览器复核，但发现问题只能退回第四层修正；
- 合并 `main`、发布版本或把方向认可写成已实现；
- 未经单独授权在其他分支实施；
- 把“推荐”“方向已确认”“规格已冻结”“执行已授权”“已实现”“已验证”混为一谈。

通常的唯一落盘例外：为了完成跨任务接力与持久化，方向聊天可以修改
`AI_CONTEXT/M0_DIRECTION/**`，并在 `context/m0-direction` 上提交、推送这些对话文档。

一次性项目入口例外：`D-M0-DIR-006` 允许本轮只在 `context/m0-direction` 修改项目根 `AGENTS.md`，加入指向本目录的最短短语路由。该授权不扩大到其他根文件、游戏代码、数据、资产、产品规格或 `main`；入口提交完成后例外结束。

### 总控授权的固定解释

`项目内持续总控`只授权第一层派发、读取、等待、审查、退回、验证、提交和推送下层结果，不授权第一层亲自修改产品文件。较早记录中出现的“第一层补修”只记录真实历史，从 v7 起统一视为流程错误，不再作为例外依据。

任何实现必须先有真实第四层任务登记。创建失败且没有安全旧线程时，状态是 `BLOCKED_THREAD`；成功创建后能力不足则清理并派发合适模型接替。第一层在两种情况下都不能接管编码。只有用户针对当次任务明确授予第一层直接修改权限，才形成一次性例外；范围结束后自动失效。

## 3. 状态词

| 状态 | 含义 |
|---|---|
| `proposal` | 助手或用户提出，尚未确认 |
| `user_confirmed` | 用户明确认可方向 |
| `spec_frozen` | 范围、规则、输入输出和验收已足以派发 |
| `dispatched` | 已由第一层交给对应层任务 |
| `implemented` | 实际文件已改变，但不代表验收 |
| `verified` | 已完成相称的自动验证或人工试玩 |
| `superseded` | 被后续决定明确替代 |
| `rejected` | 已明确否决 |
| `deferred` | 暂缓，并记录重启条件 |

`user_confirmed` 不等于 `spec_frozen`；`spec_frozen` 也不等于执行授权。

## 4. 记录内容

每个活动方向任务对应一个 session 文件。记录：

- 用户与助手所有可见消息；
- 助手 commentary 与 final；
- 证据、假设、候选方案、取舍和结论的可审计摘要；
- 新决定、未决问题、否决项与下一句建议。

对于多轮纠错和风格判断，还必须逐字保留关键用户原话、被否决候选与原因、最后接受的精确范围。不得只记录“用户要求简化”“方向已接受”等结论性摘要。

每条可能进入页面的文字必须标记一种身份：

- `discussion_only`：沟通简称、类比、内部字段和设计解释；
- `player_visible_provisional`：位置已知但用词尚未接受的临时标签；
- `player_visible_accepted`：第三层成品或用户逐字接受，可由第四层接入；
- `world_fact_only`：可供第二、三层创作的事实，不是可直接展示字符串。

未标记或只有摘要时默认 `discussion_only`。

不记录：

- 隐藏系统提示或隐式思维链；
- 原始工具噪声；
- 密钥、Token、个人凭据和无必要的本地绝对路径。

必要的脱敏必须显式记录。工具结论以事实和来源摘要保存。

## 5. 每轮持久化

一次完整回复结束前：

1. 同步远端并确认当前基线未改变。
2. 把本轮用户消息和准备发送的可见助手消息写入当前 session。
3. 更新增量理由记录。
4. 只在发生状态变化时更新 `ACTIVE.md`、`DECISIONS.md` 或 `OPEN_QUESTIONS.md`。
5. 审阅差异，确认仅触及本目录、没有秘密或冲突标记。
6. 创建文档检查点并推送。
7. 核对本地 HEAD 与远端分支头一致后，才可称为“已完成交接”。

若网络或认证失败，本轮可以继续讨论，但必须明确说明最近内容尚未传输；下一次恢复不能假定这些内容存在。

## 6. 活动写入端

- 同一时刻只有一个活动方向写入 lane；第一层总控可以常驻，同时驱动一个下层生产任务。
- 同一时刻只允许一个生产任务；并行只读比较不计为生产任务，但不得修改方向权威文件或共同写同一产物。
- `SESSION_ROUTING.md` 记录活动 lane、设备、session、路由轮次和交接目标；`ACTIVE.md` 保存热摘要。
- 正常活动使用 `routing_state: active`；当前 session 已写完交接、用户准备新建同机对话时使用 `handoff_ready`，保留当前活动字段并填写 `next_session`；原设备关闭或原 lane 不再可用而新任务尚未认领时使用 `handoff_pending`，此时活动三字段必须为 `null`。
- 同一 session 只能由一个活动方向任务追加；下层工作任务只回传产物和证据，不直接续写方向 session。
- 正常换任务时，原 lane 更新接续卡并推送；新任务从远端头读取，必要时由第一层创建新 session。
- Windows 的既有记录不得改写；当前不创建 Windows `takeover` 或备用接力任务。
- 第一层与一个下层生产任务可以同时存在，但产品文件只能由下层生产任务写入。第一层发现缺陷后通过线程消息退回，不直接修改共享工作区中的产品文件。

## 7. Git 规则

- 固定分支：`context/m0-direction`。
- 已推送历史禁止 rebase、amend 或 force push。
- 拉取只允许 fast-forward。
- 推送被拒绝表示远端出现新事实：停止，保留双方 session，再显式协调 `ACTIVE.md` 和索引。
- 已关闭 session 不修改；错误使用 amendment 记录修正。
- 未进入 GitHub 的内容一律视为未完成传输。

## 8. 文件与安全规范

- 文件名使用小写 ASCII、数字和连字符。
- 文本使用 UTF-8、LF；不依赖符号链接。
- 正文引用仓库相对路径，不保存设备绝对路径。
- 凭据、服务器地址中的秘密和私人资料不得进入记录。
- 附件只保存仓库相对路径、用途和校验摘要；大型原始材料不直接嵌入聊天文档。

## 9. 决定与冲突

- 一个结论只有一个权威落点，其他文件只引用其 ID。
- 新提案不能静默覆盖旧决定；替代必须写 `superseded_by`。
- 两个方向任务发生分歧时，冲突项回到 `OPEN_QUESTIONS.md`，由用户确认。
- `ACTIVE.md` 与 session 不一致时，以原始可见消息核对；仍不明确则标记冲突。
- 项目实现事实以代码、冻结规格和验证为准，方向聊天不得自行宣称完成。

## 10. 转入实施

只有同时满足以下条件才生成实施交接：

1. 用户明确确认方向；
2. 阻塞性问题已解决；
3. 范围、非目标、受影响系统和验收方法已写清；
4. 规格状态为 `spec_frozen`；
5. 用户对对应实现任务另行授权执行；第一层统筹或创建任务不能替代该授权。

实施任务完成后只向第一层回传改动、验证、提交和限制；不得自行改变方向。第一层再向用户呈现并决定接受、迭代或回退。

## 11. 无缝恢复验收

一个没有旧聊天历史的新 Mac 任务在五分钟内必须能说明：

1. 当前目标；
2. 最近确认的方向；
3. 提案与确认的区别；
4. 已否决或暂缓的方案；
5. 未决问题；
6. 唯一下一步；
7. 禁止操作；
8. branch、commit、session 和 turn 基线。

随后应直接继续正确问题，不要求用户复述背景。

## 12. 四层任务路由

- `WORKFLOW_BOOTSTRAP.md` 定义一句话启动、读取顺序和失败状态。
- `NEXT_ACTION.md` 是“下一步做什么、由哪条任务线负责”的唯一权威卡。
- `SESSION_ROUTING.md` 保存 16 个任务对应的稳定任务线、模型运行默认以及活动/交接状态。
- `roles/` 定义四层固定职责；层号不得重排。
- `ACTIVE_TASKS.md` 是当前任务的唯一动态路由；`TASK_PACKAGES.md` 是任务边界的固定定义。
- 同一层最多一个 `ready` 或 `active` 任务；当前阶段按任务链串行推进。
- 启动语只识别层级和任务，不授权创作、修改、提交或推送。
- 第一层可以按已满足的依赖创建、驱动、读取、等待、退回和收回下层任务；不增加第五层，也不能冒充其他层交付。
- 下层任务只回传输出和证据，不得自行推进任务路由。
- 第一层活动 lane 验收回传后，才可更新 `ACTIVE_TASKS.md`；第四层实现必须有可追溯用户授权。现有持续授权可以覆盖范围内操作，但不能替代任务卡、线程登记、白名单或阶段边界。
- 上游未冻结、角色卡缺失、写入白名单不明或 Git 分叉时必须阻塞，不得靠模型记忆补齐。
- 总规格冻结后先执行 `M0-L4-005` 外部工具能力审计，再进入 `M0-L4-010` 代码审计。能力审计只读，不授权安装；仓库状态、具体 Skill 最后提交、版本、人工评论与维护者回复日期必须分开核对。安装、全局配置、项目桥接、系统权限和常驻服务都需要用户另行授权。

## 13. 昼夜制作、弹性时长与项目归属

- 白天优先完成方向、方案、修改范围、禁止项、验收标准和测试方法；夜间只执行一项已经授权且边界明确的大结果；次日先由用户验收，再准备下一阶段。
- 每个夜间批次必须填写 `NIGHT_WORK_ORDER_TEMPLATE.md`。没有授权消息、写入白名单、输入提交、基线、验收命令和停止条件时，不得开始代码工作。
- 夜间任务通常按约六小时估算，但时间不是硬上限。仍在同一授权目标内且额度、上下文与环境足够时，可以运行八小时或更久；预计结束前约一小时转入测试、差异检查和可恢复交接。
- 延长运行不需要仅因时间经过而重新授权，但不得借此跨到下一个正式任务、扩大范围、增加权限或执行未授权的外部写入。
- 稳定 lane 复用职责与 Git 权威上下文。第一至第三层默认持续复用各自已经建立的物理会话；只有原会话已经不可恢复、系统路由失效或上下文确实无法继续承载时才建立接替会话。第四层可以按夜间批次、大阶段、上下文压力或已记录的能力不匹配定期滚动；同一稳定 lane 同一时刻仍只能有一个活动实例。
- Always Game 的所有新任务必须归入侧边栏 `always game` 项目，并使用真实仓库 `/Users/xujiangyue/AGENT Project/always game`。任何一项无法满足时必须停止并报告，不得退回通用 `xujiangyue` 项目。
- `M0-L4-401` 至 `404` 必须分别具备清楚任务卡和阶段边界；既有持续授权可以覆盖项目内实现、测试、提交和推送，不重复询问。安装、登录、系统权限、merge、deploy、发布或其他外部扩张仍需另外授权。
- 本节依据：`PLAN-M0-DAY-NIGHT-001` accepted；接受来源 `M0-S003-U089`；项目归属修订见 `D-M0-DIR-024`。

## 14. 下层任务的模型额度控制

- 第一层创建第二至第四层任务时，使用“能稳定完成任务的最低合理思考深度”，不得把 `high`、`xhigh`、`max` 或 `ultra` 当作通用默认。
- 机械核对、路径扫描、编号检查、构建和明确测试优先 `low`；需要组织多项因果、写内容结构或完成有边界的代码任务默认 `medium`。
- 只有任务涉及复杂架构取舍、难以复现的根因、互相冲突的证据，或者较低档已经出现可说明的质量失败时，才可把相关阶段提高到 `high`。升级必须在任务登记中写明原因，不扩大到整个任务的无关阶段。
- `xhigh`、`max`、`ultra` 不进入默认派发表；如确有必要，必须先向用户说明预计收益和额度代价并获得明确确认。
- 模型或思考深度不可用时，第一层选择同职责下最接近且不更昂贵的可用设置；若只能提高档位才能继续，先报告，不静默升级。
- 每张夜间执行单必须填写初始思考深度、最高自动升级档、升级条件和实际使用记录；次日交接报告是否升级及原因。
- 该规则只控制 Codex 任务额度与派发方式，不降低冻结规格、验证、证据和安全要求。依据：`D-M0-DIR-029`。

## 15. 线程新建、复用与失败重派

- `只新建一次`只约束任务创建动作本身发生错误的情形，例如创建接口报错、路由失败、任务对象没有生成。此时同一次派发只尝试一次新建，随后优先复用职责相符且状态安全的旧会话，不用相同参数连续碰运气。
- 任务对象已经成功建立并开始工作后，才出现模型理解、代码能力、架构判断或交付质量不足，属于`能力失败`，不属于`新建错误`。第一层必须先收回或关闭失败实例、确认其改动已经还原或停在可审计检查点，并记录失败证据。
- 能力失败后，可以选择更适合的模型或更高但已获规则允许的思考深度，再建立一个接替任务重新执行同一张已授权任务单。这不是对创建错误的第二次重试；接替任务不得扩大原任务范围，同一时刻仍只能有一个活动实例。
- 第一至第三层以长期积累方向、故事事实和文字风格为主，默认复用旧会话继续；第四层以代码实现和验证为主，可以按大型实施批次定期新建，避免旧上下文污染实现判断。
- 模型升级仍受第 14 节约束。只有已有可定位的能力或质量失败，才可升到 `high`；`xhigh`、`max`、`ultra` 仍需用户另行确认。
- 本节依据：`D-M0-DIR-040`，来源 `M0-S003-U136`。
