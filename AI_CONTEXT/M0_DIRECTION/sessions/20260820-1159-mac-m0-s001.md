## 推荐的一页玩法方案

推荐体验弧线：

`求生取舍 → 接纳更多人 → 暴露维护债务 → 将生存能力投射到地图外缘`

建议设置 7 次核心决策：

| 阶段 | 核心决策 | 方案方向 |
|---|---|---|
| 水源危机 | 首轮勘察优先级 | 水线、住处、维修残件 |
| 水源危机 | 长期供水方式 | 快速高维护、较慢高韧性、低物资高劳动 |
| 避难者安置 | 接纳方式 | 立即接纳、分批转移、原地支援 |
| 避难者安置 | 安置布局 | 驻地集中、修复旧区、靠近作业区分散安置 |
| 工具危机 | 当前故障处理 | 拆件应急、暂停建设抽调维修、冒险低效运行 |
| 维修瓶颈 | 长期维修制度 | 中央工场、维修轮班、外缘转存网络 |
| 高地前哨 | 路线与前哨方案 | 短陡直达、可靠绕行、补给点分段推进 |

每个选项必须同时留下四类后果：

- 地图上出现不同设施、路线或聚居布局；
- 人员、输入、维护和工期发生变化；
- 普通人的供水、劳动、住处、健康或信任发生变化；
- 下一阶段获得不同机会，而不是简单的“好结局/坏结局”。

## 二、每场聊天保存什么

每个 session 文档保存：

- 用户可见的原始消息，逐字记录；
- 助手可见的过程说明和最终回答；
- 事实与证据来源；
- 当前采用的假设；
- 考虑过的方案与取舍；
- 已确认、待确认、否决、推迟的内容；
- 本场结束摘要和下一步。

每轮使用固定 ID，例如：

```text
M0-S001-U001    用户消息
M0-S001-A001    助手回答
M0-S001-R001    对应的决策理由记录
```

“思路”保存为可审计记录：

```text
证据 → 假设 → 候选方案 → 利弊取舍 → 当前结论
```

不会保存系统隐藏提示、隐式思维链、完整工具噪声或密钥；工具产生的重要事实会被整理成证据记录。这样可以复现判断过程，又不会把敏感信息永久写进 Git 历史。

## 三、ACTIVE 接续卡

`ACTIVE.md` 必须很短，建议不超过 200 行，包含：

- 已确认的 3–5 项决定；
- 尚未确认的最多 3 个问题；
- 被明确否决的方向；
- 唯一下一步；
- 不允许扩展的范围；
- 当前分支、远端提交、最后 session 和 turn ID；
- 当前写入设备：`mac` 或 `windows`；
- 下一场聊天可以直接使用的开场指令。

任何新聊天只需要先读这张卡，不需要加载全部历史。

## 四、Mac 与 Windows 的接力流程

推荐固定使用远程分支：

```text
context/m0-direction
```

未确认的讨论留在该分支；M0 产品契约冻结后，再经用户授权合并到 `main`。

每次完成一个用户—助手回合：

1. 把本轮可见内容写入当前 session。
2. 更新可审计思路和阶段摘要。
3. 如果出现新结论，更新 `ACTIVE`；只有明确确认的内容才能进入产品契约和决策日志。
4. 创建文档检查点并推送到固定分支。
5. 推送失败时明确标记“尚未完成交接”，不能假装已同步。

Mac 切换到 Windows 时：

1. Mac 关闭当前 session，并将其标记为不可再修改。
2. 更新 `ACTIVE`、未决问题和会话索引。
3. 检查没有秘密、冲突标记或未记录结论。
4. 同一次提交、同一次推送完成交接。
5. Windows 只允许快速同步远端最新版本。
6. Windows 创建新的 session，不继续修改 Mac 已关闭的文件。
7. 新聊天先输出“恢复回执”，再继续讨论。

恢复回执必须说明：

- 当前目标；
- 最近一次确认决定；
- 被否决的方案及原因；
- 尚未解决的问题；
- 下一步；
- 禁止扩展的范围；
- 当前分支、提交、session 和 turn。

如果 Mac 没来得及正式交接，但最后一轮已经推送，Windows 可以创建一条 `takeover` 记录接管；旧 Mac 再回来时必须先同步，不能继续写旧 session。
