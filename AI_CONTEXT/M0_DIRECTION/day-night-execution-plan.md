# 昼夜制作计划

## 一句话规则

白天把方案、范围和验收标准说清楚；晚上只执行已经授权、能够独立收尾的一段工作；第二天先看结果，再决定是否进入下一段。

六小时只是夜间任务的初始工作量估算和排期参考，不是停止上限。只要仍在同一个已授权目标内，可用额度、上下文和运行环境足够，而且继续执行能形成更完整的结果，就可以运行八小时或更久。任务提前完成就提前停；不得为了延长时间扩大范围或自动跨到下一个正式任务。

## 白天：把夜间任务准备到可以直接执行

白天只做方向判断、系统设计、方案比较、任务拆分和验收口径。每个准备放到夜间的任务，必须先形成一张 `NIGHT WORK ORDER`，至少写清：

- 夜间批次编号、所属正式任务编号、唯一目标、非目标和预期产物；
- 允许修改的文件或模块白名单，以及明确禁止触碰的范围；
- 用户授权消息编号；
- 开始分支、提交、工作区状态和回退锚点；
- 修改前基线与需要保留的既有行为；
- 完成标准、验收命令、测试项目、基线结果和失败判定；
- 可独立验证的阶段检查点；
- 必须读取的权威文件清单；
- 开始时间、预计耗时区间、首次收尾判断点，以及遇到歧义、权限、依赖、环境故障或额度不足时的停止条件；
- 是否允许本地提交、远端推送和其他外部写入，以及相应回退办法。
- 任务模型、初始思考深度、最高自动升级档和可核对的升级条件。

没有完整执行单或没有对应实施授权的任务，不进入夜间代码阶段。

## 晚上：一个大结果，通常按约六小时估算

建议按下列节奏执行。时间随任务大小伸缩，不要求在第六小时强制停止：

| 阶段 | 时间参考 | 主要工作 |
|---|---|---|
| 预检 | 开始后约 20 分钟 | 核对任务卡、分支、授权、工作区、依赖和基线测试 |
| 主要执行 | 占预计时长的大约 70%—80% | 完成主要修改与针对性测试；最多拆成两至三个彼此连贯、可以分别验证的阶段 |
| 收尾 | 预计结束前约 1 小时 | 停止新增功能，完整复核改动、回归测试、检查差异、形成提交和次日交接 |

约第五小时进行一次继续判断：如果剩余工作仍属于同一个目标、额度和上下文足够、没有出现新设计问题，就把预计结束时间顺延到八小时或更久，并重新预留最后约一小时用于收尾。继续执行不需要为了“超过六小时”重新授权，但绝不能借此跨任务、扩范围或跳过新的权限门。

夜间执行遵守以下边界：

- 一次只追求一个明确的大结果，不同时研究新方向和写代码；
- 一个大阶段只有在自然包含多个可独立验收的结果、单次上下文承载风险过大，或当晚额度不足时，才拆成同一正式任务内的 A/B/C 夜间批次；不得跨到下一个正式任务；
- 只在已接受的执行单内自行推进，不临时新增玩法、架构目标或验收口径；
- 不自行安装或升级依赖、登录账号、处理密钥、扩大系统权限、修改常驻服务、执行数据迁移或引入新的外部工具；远端推送、合并、部署和其他外部写入也必须由执行单明确授权；
- 普通小问题可以在既定目标内修正；出现会改变方案的歧义时，停止该项并记录，不替用户作新决定；
- 每完成一个可验证阶段就留下检查点；连续工作约两小时仍没有检查点时，优先收束当前修改；
- 预计结束前约一小时必须转入测试、差异检查和可恢复交接，不用来开启新内容；延长运行时同步顺延收尾时段；
- 提前达到验收标准就立即停止，不为了跑满预计时长扩展范围；
- 无人值守时不等待临时授权；遇到授权门或登录交互，写清阻塞并安全退出。
- 机械扫描、构建和明确测试优先使用 `low`；有边界的代码实现默认 `medium`。只有复杂架构、难复现根因、冲突证据或较低档明确失败时，才把必要阶段升到 `high`；`xhigh`、`max`、`ultra` 必须先获用户确认。

出现以下任一情况，立即停止新增修改并进入收尾：

- 开始分支、提交或输入版本与执行单不一致；
- 工作区出现执行单没有登记的既有改动，无法确认归属；
- 需要越出文件白名单、作出新设计决定、增加权限或进行破坏性操作；
- 与本任务无关的基线测试失败，无法确认本轮修改是否安全；
- 同一根因连续修正两次仍失败；
- 剩余额度、上下文或运行条件不足以同时完成修改、验证和可恢复交接；
- 上下文或工具输出已经过大，继续工作可能无法留下完整交接。

## 安全停止状态

每次夜间运行只能停在以下明确结果之一。这些是 `night_run_status`，不替代 `ACTIVE_TASKS.md` 的正式任务状态：

- `completed_waiting_review`：本批目标完成，正式任务进入或保持 review，等待用户查看；
- `blocked_design`：需要新的设计决定；
- `blocked_auth`：缺少用户授权或外部账号授权；
- `blocked_environment`：依赖、构建、系统或网络环境阻塞；
- `budget_or_runtime_checkpoint`：额度、上下文或运行条件不足，当前工作已停在可恢复检查点；
- `context_checkpoint_required`：模型上下文接近上限，已写完交接，必须新建任务继续。

停止时不得把部分完成写成全部完成，也不得因为时间已到而跳过验证。未完成但可继续的正式任务保持 active；只有完整候选才进入 review；用户接受后才可变成 accepted 或 verified。

## 防止上下文耗尽

- 每个夜间任务只承载一个主要结果；研究、方案确定和实现分开进行；
- 稳定 lane 和职责可以延续，但物理 Codex 任务按夜间批次、大阶段边界或上下文压力滚动新建；同一时刻仍只能有一个活动实例；
- 不把全部历史聊天重新粘贴进新任务；
- 新任务只读取权威文件、当前执行单和必要代码，历史结论通过文件路径引用；
- 交接只保留已确认决定、当前假设、完成内容、测试结果、未完成项、阻塞和下一目标；
- 网页证据、构建日志和测试输出设定数量上限，只保留支持结论的必要部分；
- 长时间任务在每个检查点更新短交接；发现重复读取、大段输出或剩余上下文明显不足时，先收尾，再换新任务；
- 一旦出现 context-window 错误，不在原任务里反复重试；新任务只读取最近的 Git 检查点和执行单继续；
- 边界清楚的代码任务可继续使用 5.3；一次需要大量网页证据、长文档与多候选比较的工作要拆批，必要时改用更适合长上下文的模型。
- 模型替换和思考深度升级是两件事；不能因为换了模型就自动提高思考深度，也不能用高思考深度代替缩小证据范围、限制日志或拆分任务。

## 第二天：先验收，再继续

次日交付必须先写结果，再列证据：

- 完成了什么，哪些没有完成；
- 夜间批次编号、所属任务、实际耗时和停止原因；
- 输入提交、输出提交和回退锚点；
- 修改了哪些文件；
- 运行了哪些测试，通过数、失败数和已知失败是什么；
- 本地提交与远端推送是否成功；
- 当前阻塞、风险和需要用户决定的唯一下一步；
- 实际使用的思考深度、是否发生升级和升级原因；
- 有界面变化时附上必要截图或可检查产物。

用户接受或退回本轮后，白天再准备下一张夜间执行单。夜间任务完成不自动授权下一个大阶段。
