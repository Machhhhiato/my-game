# M0 方向讨论决定

> 本文件只记录 `context/m0-direction` 上经用户明确确认的方向决定。
>
> 这些决定约束后续方向讨论；在独立同步聊天将其写入项目冻结规格前，不得被实施聊天直接当作已冻结任务包。

## D-M0-DIR-001 · GitHub 对话接力协议

- 日期：2026-08-20
- 状态：`user_confirmed`
- 来源：`M0-S001-U002`、`M0-S001-U003`
- 决定：
  - GitHub 是跨电脑、跨聊天、跨项目外壳和跨终端的唯一传输层。
  - 使用固定分支 `context/m0-direction`。
  - 一场聊天对应一个 session；保存可见原文和可审计理由。
  - `ACTIVE.md` 作为热接续卡，session 作为追溯来源。
  - 同一时间只允许一个活动写入端；已推送记录不得强制覆盖。
- 不采用：
  - 依赖 ChatGPT Project、聊天同步或云项目。
  - 一份由两台电脑共同无限追加的单体聊天文件。
  - 只保存结论、不保存讨论来源。

## D-M0-PROD-001 · 为资深玩家本人定制并先免费发布

- 日期：2026-08-20
- 状态：`user_confirmed`
- 来源：`M0-S001-U004`
- 决定：
  - 游戏当前首先为用户本人量身定制；用户是资深策略玩家，也是 M0 的第一验收人。
  - 当前不考虑买断、定价或商业回报，不以大众市场转化约束 M0 核心体验。
  - 初版只有在用户本人认可后，才进入首次公开发布。
  - 首次公开发布路径为 Steam 免费游戏。
- 边界：
  - Steam 免费不自动等于 F2P、广告、内购、赛季或持续在线运营。
  - 是否永久免费以及后续商业方式均为 `deferred`。
  - 用户认可优先于外部测试；发布前是否安排少量资深玩家兼容性测试仍是 `proposal`。

## D-M0-PROD-002 · 专业管理形成科技、资产与版图领先

- 日期：2026-08-20
- 状态：`user_confirmed`
- 来源：`M0-S001-U005`
- 核心爽点：
  - 拥有更多高科技、技术与资源优势、地图控制、高级资产、奇观、军队、舰船、军舰和航母等可见对象。
  - 通过操作和微调集中资源，抢先突破关键科技，并把领先转化为真实资产和扩张能力。
  - 国家内部资源与政策形成良性循环，在压力和危机前拥有足够储备。
- 设计规则：
  - 重大科技必须沿“研究 → 设计/工程 → 制造 → 部署 → 地图或运行结果”形成可拥有对象，不能只给抽象百分比。
  - 优势允许正向累积：科技促进生产与勘探，资产扩大资源和版图，新增资源反哺科研、生产与储备。
  - 危机是准备度考试；预警、储备、冗余、维护和正常经营应能完整解决问题。
  - 主要选择是顺序、效率、产能、扩张速度和储备目标，不以强制极端匮乏或二元道德困境制造戏剧性。
  - 极端方案只能作为长期失误后的可选应急路径，不能是正常成功路线的必经门。

## D-M0-PROD-003 · 玩家突破与系统自动推进并存

- 日期：2026-08-20
- 状态：`user_confirmed`
- 来源：`M0-S001-U006`
- 决定：
  - 玩家可以协调科研、预算和产能，集中资源抢先完成关键科技。
  - 玩家想放松时，系统可以自动推进中间过渡与普通科技，形成看海阶段。
  - 自动科研必须受玩家选择的科技领域倾向约束，并允许随时接管。
- 待冻结提案：
  - 双层科研分为手动“重点突破”和自动“领域推进”。
  - 领域倾向先使用重点、正常、维持、暂停四档，不在 M0 使用复杂百分比面板。
  - 核心突破、路线分叉、重大资产和不可逆制度不允许系统擅自决定。

## D-M0-PROD-004 · 自动资源必须来自实体体系

- 日期：2026-08-20
- 状态：`user_confirmed`
- 来源：`M0-S001-U006`
- 决定：
  - 自动资源获取不能是科研完成后凭空增加的抽象日产量。
  - 每类资源必须有与其性质相符的独立系统或前哨设计，例如农田、给排水、水厂、废墟勘探与回收。
  - M0 第一条链必须到达可日常独立运行、持续向总部输送资源的前哨。
- 通用实体链：资源地点 → 生产/采集 → 当地加工 → 仓储 → 运输路线 → 总部流入。
- 边界：独立运行代表日常自治执行，不代表免维护、无限资源或独立主权。

## D-M0-PROD-005 · 首建形成可复制的标准工程经验

- 日期：2026-08-20
- 状态：`user_confirmed`
- 来源：`M0-S001-U007`
- 决定：
  - 每一种前哨或资源工程类型第一次建立时，都要经历选址、探索、场地清理、应用科研、测试、工程建设、试产和稳定验收。
  - 首次稳定运行后，国家获得该类型的生产与工程经验；后续同类前哨只要找到合适选址，就可以由系统一条龙自动完成，不再要求玩家重复操作。
  - 首建的核心挑战是协调有限资源和人力，而不是逐项点击施工步骤。
- 边界：经验消除重复管理，不消除真实的人力、物资、时间、运输和维护成本；超出既有适用条件时仍需要工程适配。

## D-M0-PROD-006 · 地形适配与有限人力构成前哨约束

- 日期：2026-08-20
- 状态：`user_confirmed`
- 来源：`M0-S001-U007`
- 决定：
  - 地图骨架必须表达山地、泥地、河边、沙滩、矿产资源、城市废墟等土地与资源条件，并据此约束工程选址。
  - 不同工程有不同的硬性选址要求；农田不能无条件建在城市废墟或山地，矿山必须依附矿藏，废墟回收必须依附可回收遗址。
  - 首建阶段重点考验有限人力在日常资源生产、科研、勘测、工程建设、物流与继续开拓之间的协调。
- 待冻结提案：地图采用区域节点、候选工程地块和交通连接；地块以地貌、水文、资源覆盖、工程风险和交通条件分层表达。
