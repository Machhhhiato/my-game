# M1 系统统一原子拆分与验收合同

本合同约束剩余系统规格，系统组名称只用于沟通，不是科技树节点。

每个系统必须分别列出：容量/服务类别、明确产品或服务、设施、组织、实际单科技、每项科技的多个独立解锁对象、法令、有限期政策、状态、月结算输入输出、第2年存在事实和旧数据类型修正。

统一硬规则：

1. 一项科技只研究一种可复现能力，但可以分别解锁多个明确对象；多个对象必须各自拥有 ID、类型和关系。
2. 科技不直接生成产品、设施、组织或状态；真实投入、人员、建设、运行和验收成立后才产生结果。
3. 工厂类别、厂址、生产线、产品、设施、组织、工程、法令、政策、行动、记录、状态和服务流不得互相冒充。
4. 生产线只形成一个明确主产品；同一产品可由不同路线生产，路线与批次保存差异，不滥增产品 ID。
5. 过细零件、岗位小件和同一任务必需组件可以适度组成套装；工艺、用途、短缺后果或里程碑不同的对象必须分开。
6. 每个制造产品使用拟真型号族或材料牌号；具体额定参数可在数值阶段填写，型号改进通过实际运行结果体现。
7. 所有系统复用统一月结算的资产容量、投入满足率、人员组织、设备状态、地点可达性、流量、库存、损耗和维护逻辑。
8. 地点化服务不能全国无损共享；跨地点转移必须通过真实网络或物流任务。
9. 常设法令长期约束对象；政策必须有触发、代价和退出条件；状态只读取实体与运行证据。
10. 两年是主线与科研难度参考，不是科技日期门；真实前置满足即可提前研究。
11. 实际展示只出现单项科技与独立产物，不出现系统总结节点、阶段标题或沟通用路线名。
12. 每个系统结束必须通过 ID 唯一、对象类型、数量、前置、跨系统输入输出和第2年存在性审计。
13. 系统只是导航、预算和状态汇总边界，不是实际对象；多个系统可以收进一个玩家页面，但科技、产品、工程和法令的身份不得因此合并。
14. 日常值班、登记、调度、检查、验收、调查和复盘不自动成为科技。只有需要研究、试验、验证并能复制的新能力才进入科技树；其余分别作为行动、记录、状态或组织规程。
15. 一个物理对象只有在玩家需要独立生产、库存、调度、短缺判断或型号迭代时才成为玩家产品；在制品、批次状态、现场即产即用流和没有独立决策价值的内部部件留在配方、工程物料清单或设备型号中。
16. 精简只能逐项删除、重分类、判重或移到后期路线；禁止把多个独立对象换成一个带“综合”“一体化”或并列名称的新对象。精简后的每项科技、产品、工程和法令仍必须拥有唯一 ID。

为压缩方向规格篇幅，`ID 范围 + 依次列名`只允许出现在本轮设计表中，并严格按从左到右映射：第一个名称对应`001`、第二个对应`002`，依次类推。进入 R5 数据、实际科技树、玩家展示或实现任务前必须展开为逐项独立对象；任何范围行、分号清单或“综合系统”不得成为实际对象。

十万人规模的玩家系统与产品精简边界以`SPEC-M1-LEAN-SYSTEM-PRODUCT-ARCHITECTURE-001`为当前修订来源。原12项连续系统规格继续作为完整性来源，不再具有“全部新增科技直接进入R5”的含义。
