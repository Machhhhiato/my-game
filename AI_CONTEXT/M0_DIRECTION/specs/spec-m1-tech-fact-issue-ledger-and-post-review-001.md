# 科技事实问题标签账与正文完成后整树复审

## 1. 目的

逐项正文打磨会迫使审查者真正解释每项科技，因此也是发现科技树结构问题的最佳时机。发现的问题必须在当项登记，不能等全文完成后凭印象回忆；正文全部完成以后，再把单项证据放回整棵树中统一判断保留、合并、拆分、删除、下沉、改前置或改解锁。

本账是内部设计工具，不进入科技卡、页面、日志或玩家正文。

## 2. 单项标签

| 标签 | 何时使用 | 默认是否阻塞正文 |
|---|---|---|
| `MERGE_CANDIDATE` | 与其他节点可能只是同一玩家里程碑的不同内部步骤 | 结合全树才能判断时否；已经确定重复时是 |
| `SPLIT_CANDIDATE` | 一个节点包含多个不可互换的科技能力 | 是 |
| `REMOVE_CANDIDATE` | 没有独立玩法价值或只是现实手续 | 结合全树才能判断时否；已经确定时是 |
| `DEMOTE_CANDIDATE` | 更适合作为解锁、工程、设施、产品改型、组织运行、政策、法律或法令 | 结合全树才能判断时否；已经确定时是 |
| `PREREQUISITE_ERROR` | 前置缺失、重复、倒置或错误跨支 | 是 |
| `UNLOCK_MISMATCH` | 解锁重复、缺失、越级、类型错误或不由本科技产生 | 是 |
| `SCALE_ERROR` | 节点过细、过粗，或不符合战略挂机游戏的操作尺度 | 视证据而定 |
| `DUPLICATE_MILESTONE` | 不同节点给玩家相同进步感或相同主要产物 | 结合全树裁决 |
| `LOW_GAME_VALUE` | 现实合理，但对玩家没有独立决策、期待或反馈 | 结合全树裁决 |
| `SOURCE_MISSING` | 缺少证明节点成立的上游事实 | 是 |

阻塞项必须停在`fact_gate: return/blocked`。非阻塞项只能使用`fact_gate: pass_with_tree_review`，不得伪装为无问题的`pass`。

## 3. 每条记录的固定字段

```text
tech_id:
current_name:
fact_gate:
issue_tags:
issue_statement:
evidence:
related_tech_ids:
blocks_prose: true / false
provisional_post_review_action:
raised_at:
resolution_status: open / resolved_locally / waiting_post_tree_review / superseded
```

`issue_statement`必须具体说明哪里冲突；`evidence`必须指向正式对象、相邻节点、产物、工程、系统规格或玩家操作；`provisional_post_review_action`只是复审建议，不能提前修改正式树。

## 4. 正文完成后的全树复审

全树复审覆盖全部科技，不只覆盖已有标签。每项必须比较直接前置、直接后继、同分支和可能重复的远处分支，并检查产品、工程、设施、工厂、组织、政策、法律、法令与部队是否能够承接它。

每项提出一个主裁决：

| 裁决 | 通过条件 |
|---|---|
| `KEEP` | 玩家失去该节点会失去一个清楚、可感知、不可替换的能力或文明里程碑 |
| `MERGE` | 多个节点共同构成一个玩家里程碑，拆开只增加等待和按钮，不增加不同选择 |
| `SPLIT` | 当前节点内部存在多个可以独立前置、独立解锁和独立反馈的科技 |
| `REMOVE` | 只是真实社会细节、手续或重复解释，没有独立游戏价值 |
| `DEMOTE` | 内容仍需存在，但更适合作为解锁、工程、设施、产品改型、组织运行或制度对象 |
| `REWIRE_PREREQUISITE` | 科技保留，但知识、产业、能源、维护或组织前置关系错误 |
| `REWRITE_UNLOCK` | 科技保留，但直接效果需要去重、补全、拆清或降级 |

## 5. 游戏设计复审标准

1. 玩家是否会期待研发完成，并能立即说出得到了什么；
2. 节点是否产生新产品、新工程、新设施、新组织、新战术、新生产方式或新的可靠判断能力；
3. 与相邻节点相比，是否只是同一操作的内部步骤或同义重复；
4. 是否把现实中必要的手续误做成科研按钮；
5. 是否保留产品代际、装备型号、工厂扩建、生产方式和战术变化带来的进步感；
6. 科研点、资源、人口、工程与维护成本是否配得上节点的重要性；
7. 节点数量和分支密度是否超过玩家能够理解和操作的尺度；
8. 合并后是否仍是一项真实科技，而不是方向总结；
9. 删除或下沉后，原有产物、工程、政策和前置关系是否仍有明确归属；
10. 整棵树是否形成连续的能力增长，而不是大量手续之间夹着少数真正里程碑。

## 6. 修改边界

整树复审先交付裁决提案与影响表，不直接修改正式科技JSON。任何结构变化都必须列出受影响的科技ID、名称、正文、科研点、解锁、前置、后继与跨支关系。用户确认后，只返工受影响对象；未受影响的已接受正文逐字保留。
