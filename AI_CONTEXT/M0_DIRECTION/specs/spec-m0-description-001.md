# SPEC-M0-DESCRIPTION-001 · M0 工程与科技描述结构、风格与总规格冻结

## 1. 本规格决定什么

本规格只决定工程、科研、设备、阶段报告、维修和制度类文字怎样组织。科研候选卡先服务快速比较，完整正文再解释技术与世界内情况；需求、时间、阻断和实时状态放在真正负责这些信息的项目页或状态页，不能把所有底层字段挤进一张科研卡。

本任务不写具体负责人的完整故事，不写最终科技正文，不修改已经接受的机制、数字和结果，也不修改游戏代码。只有本规格逐项被用户接受，并最终整体接受后，才可以把 `overall_spec_frozen` 标为 true。

## 2. 已接受输入与不能改动的事实

- 科研完成只解锁图纸、方法、工程或制造条件，不直接生成设施、设备、产量、库存或地图情报。
- 实体能力必须经过制造或修复、运输、部署、标定、配人、供能和维护中实际需要的环节，才对指定阶段生效。
- 第一座前哨首次阶段报告仍可说明新事实、工程影响、当前需要、完成结果和下一步，但不能把内部工序拆成玩家状态；没有真实选择时不暂停工程。
- 第二座复制与重复建设的普通进展进入短日志；只有新事实、真实选择、阻断和验收完成才主动提示。
- 玩家侧科技只有未研发/已研发，工程只有在建/已建成；进行中只显示进度、已投入物资和占用人力。部署预计、前后预计耗时与完成快照只留底层模型，不作为玩家展示。
- 所有人员、物资、工作量、地点、设备状态、暂停原因和恢复条件都引用已接受的真实状态，不新增“文案专用”变量或效果。
- 来源附件只提供通用规则：技术本身可信，荒诞主要来自制度怎样解释结果；不复制或仿写小说原文、章节与专有名词。

### 6.1 第一版为什么撤回

用户在 `M0-S003-U045` 指出，第一版“恢复精密制造”仍然是在解释研究解锁什么、还缺什么和系统怎样运行，不是一篇玩家会阅读的科技正文。尤其是“研究完成后只解锁……”一段属于玩法说明，应由已接受的效果行、工程页与状态页承担，不能冒充世界内文字。

### 6.2 当前正文边界

- 正文只写世界内部存在的设备、工艺、试验、使用和制度后果，不出现“玩家、本科技、解锁、效果、前置条件、工程页面”等系统外语言。
- 世界内参数可以出现，例如公差、温度、连续运转时间和报废件数；`+5%`、科研工作量、内部等级和状态字段不能混入正文。
- 卡片效果负责告诉玩家研究后得到什么；工程页只显示进度、已投入物资和占用人力，其他地点、时间、阻断与恢复条件继续由底层模型负责；正文不重复系统显示。
- 删除制度性结尾后，前面的技术过程仍必须可信；制度荒诞来自验收、统计、程序或成本怎样解释结果，而不是技术本身故意失效。

## 8. 第四项提案：原页面、日志和一次通知

### 8.1 只保留三个地方

1. `原页面`：玩家想看当前情况时，回到对应科技、工程或设施页面。科技显示未研发/已研发和进度；工程显示在建/已建成、进度、已投入物资与占用人力；设施显示自身当前运行情况。
2. `日志`：保存已经发生的事和需要阅读的完整文字。首次工程的专业人员文字、事故经过和恢复结果都可以回看，但日志不会把底层工序变成新状态。
3. `通知`：只在某件事发生变化时出现一次，点击后跳到对应页面或日志。通知不要求确认，不制造额外完成按钮，也不自动暂停整个游戏。

不再为科研、工程、事故、验收和维护分别造一套窗口。它们使用同一套页面、日志和通知，只是写入的内容不同。

### 8.2 各类内容怎样进入这三个地方

| 内容 | 玩家在哪里看 | 是否主动通知 |
|---|---|---|
| 科研进行中 | 科技页只看进度 | 不通知 |
| 科研完成 | 科技页变为已研发；结果写日志 | 通知一次；自动队列能继续时不打断 |
| 科研遇到必须由玩家决定的互斥分支 | 科技页等待选择；原因写日志 | 保留一条通知直到选择；科研线可以停，但不暂停整个游戏 |
| 工程普通进度 | 工程页看进度、投入物资和占用人力 | 不通知 |
| 首座工程首次阶段文字 | 写入该工程的建设记录，项目上显示未读标记 | 不弹窗，不把阶段变成状态 |
| 第二座与重复建设的普通过程 | 只保留必要短日志 | 不通知 |
| 工程建成或稳定验收完成 | 工程页变为已建成；结果写日志 | 通知一次，不增加`待验收`状态或确认按钮 |
| 事故发生 | 设施或资源页显示真实影响，经过写日志 | 保留一条可点击通知，不按日重复刷屏 |
| 事故修好或自然结束 | 设施状态恢复，结果写日志 | 原事故通知改为已解决，不新增“挑战通过”弹窗 |
| 工程或科研无法继续 | 对象仍保持未研发或在建，底层保存真实原因 | 保留一条通知；条件恢复后按既有授权自动继续或清除 |
| 日常维护正常运行 | 设施页可查，普通结果进短日志或不记录 | 不通知 |
| 维护积压已经影响设施 | 按事故处理 | 状态变化时通知一次 |

### 8.3 最小规则

- 当前情况回原页面看，发生过的事情进日志，值得注意的变化通知一次。
- 相同问题没有发生新变化时不能重复发通知；日志可以继续记录底层结算，但不刷玩家屏幕。
- 首座首次阶段文字完整保留在工程建设记录里，不作为七次弹窗，也不产生七种工程状态。
- 科研自动轮次、第二座自动复制和日常维护只要能按玩家既有授权继续，就不请求确认。
- 只有规则确实要求玩家作出无法自动决定的选择时，对应项目或科研线才等待玩家；整个游戏不因普通通知自动暂停。
- 事故不是选择题、考验模式或奖励节点。发生时通知一次，修好后自然结束，通知标记为已解决。
- 本项只冻结内容去哪里和何时通知，不冻结通知窗口外观、位置、声音、颜色或最终 UI。

第四项当前为 `active_review`。用户接受前不进入第五项。
