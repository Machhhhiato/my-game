# 可复用月度资源结算内核

## 1. 第一规则：同一种数量变化只允许一套计算逻辑

凡是可以表示为“来源在一个月内提供数量，经过真实限制后进入库存、被当月使用或累积为项目进度”的对象，都必须使用本规格的统一月度账本、统一分段公式和统一结算顺序。

科研、工程、训练、维修、生产、运输和行政执行不得各自发明`科研速度`、`建造速度`、`训练速度`、`维修速度`等互不兼容的计时公式。它们只提供不同的单位、来源、目标、必要输入和完成条件，计算内核保持相同。

统一不等于把所有世界事实压成一个数。人口、设施、地点、车辆、部队、协议、伤病、战争和事件仍是具有身份和状态的对象；它们可以成为账本来源、目标或限制器，但不得为了复用公式而丢失对象语义。

## 2. 统一账户只有三类

| 账户类型 | 月初余额 | 月末处理 | 例子 |
|---|---:|---|---|
| `stock` 库存 | 上月结余 | 入库、消耗、容量与损耗后继续结转 | 水、食物、材料、零件、燃料、药品、弹药 |
| `flow` 当月流量 | 固定为 0 | 当月生成并分配，未使用部分失效 | 科研点、工程工时、训练工时、维修工时、运输能力 |
| `progress` 项目进度 | 上月累计 | 接受对应流量，达到目标后完成 | 科技、工程、训练、维修、统合项目进度 |

实体和状态不建立第四种数量账户。实体的库存、状态恢复或项目完成可以读取这三类账户，但实体本身仍由稳定 ID 和真实状态保存。

## 3. 所有月度来源共用四个计算变量

每个来源只允许使用以下四个一级计算变量：

1. `baseMonthlyRate`：一个标准有效单位在完整月份中的基础产出；
2. `activeCapacity`：本分段实际投入的合格人员、设施、生产线、车辆或组织容量；
3. `efficiency`：本分段真实状态形成的综合效率；
4. `monthFraction`：本分段实际天数除以当月实际天数。

统一公式固定为：

```text
offeredAmount = baseMonthlyRate × activeCapacity × efficiency × monthFraction
```

不得再为不同领域增加平行的速度乘区。专业匹配、熟练度、设施状态、组织协同和可恢复的环境影响都先归并为可追溯的 `efficiency`；人员或设施数量归入 `activeCapacity`；时间只归入 `monthFraction`。

`efficiency` 可以由多个事实计算，但最终必须保存来源明细并合成为一个 0 以上的有限值。缺少不可替代的硬条件时，不把效率设成极小数继续运行，而是由限制器把实际交付降为 0。

## 4. 所有领域共用限制器

来源提出 `offeredAmount` 后，使用同一种限制器列表确定实际可交付数量：

- 必要输入能支持的最大数量；
- 路线或网络能传递的最大数量；
- 目标库存剩余容量或项目剩余工作量；
- 安全、资格、地点、设备和其他硬前置允许的最大数量；
- 玩家批准的分配份额、优先级或队列顺序。

```text
deliverableAmount = min(offeredAmount, inputLimits..., routeLimits..., targetLimit, authorizationLimit)
```

输入只按 `deliverableAmount` 实际消耗，不按未实现的 `offeredAmount` 预扣。任何限制器都必须指向真实对象和原因，不得使用无法追溯的领域专属减速常数。

## 5. 月内变化统一封存分段

1. 游戏继续逐日推进事实，但数量账户按公历月正式结算。
2. `activeCapacity`、`efficiency`、输入、路线、目标或分配变化时，立即封存旧条件分段，并以新条件记录剩余月份。
3. `monthFraction = segmentDays / daysInCalendarMonth`，自动适配 28、29、30、31 日月。
4. 分段只保存计算所需事实和结果，不建立科研日进度、生产日进度或其他领域专属日账。
5. 预计库存会在月内耗尽时，统一计算首次耗尽日并封存新分段；账户不得出现负库存，也不得让依赖该库存的来源继续运行。
6. 一次性收支在事实发生时立即写入当前月账本并改变可用库存；月末报告汇总它们，但不得延迟实际扣除。

## 6. 统一分配和队列规则

1. 一个来源可以按玩家批准的份额、优先级或队列向多个目标交付，但分配总量不得超过 `deliverableAmount`。
2. `stock` 目标接收到容量上限；超过容量的部分必须有明确溢出、转运、损耗或停止规则。
3. `flow` 账户月初和月末均为 0；未分配部分失效，不能伪装成库存。
4. `progress` 目标接收到目标工作量；达到目标后完成，超出部分只能按同一已批准队列继续分配给随后满足前置的项目。
5. 没有合格后续目标时，剩余流量失效。已经进入具体 `progress` 账户的数量永久保存，不因暂停、换队、故障或改优先级清空。
6. 多个来源投入同一目标时先分别计算、再统一合并；目标的协同上限作为限制器，不另建领域专属并行公式。

## 7. 固定月结顺序

进入下月第 1 日时，所有适用领域必须按同一顺序处理：

1. 封存上月最后分段；
2. 根据月内真实短缺、故障、停工、伤病和路线状态确认各分段有效条件；
3. 计算每个来源的 `offeredAmount`；
4. 应用输入、路线、目标和授权限制器，得到 `deliverableAmount`；
5. 按批准分配写入 `stock`、当月使用或 `progress` 账户，并按实际交付扣除输入；
6. 处理库存容量、损耗、短缺和即时交易汇总；
7. 确认本次达到目标的项目和永久状态变化；
8. 新完成项目的影响从新月份开始，不追溯修改已结算月份；
9. 生成唯一月结记录和下月预测。

同一结算图中不得依靠循环引用从零产生资源。存在循环生产链时，必须有上月库存、外部输入或明确启动资产作为种子，并以守恒检查证明没有免费产出。

## 8. 统一持久化和审计字段

每个账户、来源、目标和分段至少共用以下字段，不再复制领域版本：

- 稳定对象 ID；
- 账户类型与计量单位；
- 月初余额、当月流入、当月流出、月末余额；
- `baseMonthlyRate`、`activeCapacity`、`efficiency`、`monthFraction`；
- 输入限制、路线限制、目标限制和授权限制的来源；
- 分配目标、优先级或队列顺序；
- 已封存分段与一次性收支；
- 完成、短缺、溢出、损耗或失效结果；
- 下月预测。

所有浮点数量在持久化和前端序列化前统一保留至多两位小数；比较与结算使用固定舍入规则，同状态、同指令和同公历月份必须得到相同结果。

## 9. 领域只能提供配置，不得复制内核

| 领域 | `flow` 单位 | 典型来源 | `progress` 或 `stock` 目标 |
|---|---|---|---|
| 科研 | 研发点 | 科研岗位与研究设施 | 具体科技项目进度 |
| 工程 | 工程工时 | 施工队与工程设备 | 具体工程项目进度 |
| 训练 | 训练工时 | 教官、场地与装备 | 具体人员或部队训练进度 |
| 维修 | 维修工时 | 维修岗位与工场 | 具体设施、车辆或装备维修进度 |
| 生产 | 产品数量 | 生产线与工厂 | 对应产品库存 |
| 运输 | 运力 | 车辆、路线与调度 | 当月实际货物转移 |
| 行政统合 | 执行量 | 登记、服务与行政岗位 | 具体聚居点统合项目进度 |

领域规格只允许填写基础月产率、容量来源、效率事实、输入系数、限制器、分配和完成结果。若新增领域必须再写一套速度、分段、结算或持久化逻辑，视为违反本规格。

## 10. 不强行统一的边界

- 战斗命中、外交选择、事件分支、人物态度、具体伤病、出生和死亡等离散因果仍由各自状态机处理；其产生的资源收支统一写入月账，但选择和因果本身不能压成流量公式。
- 产品、设施、部队、人口和地点不能因为拥有数量字段就降格为通用资源；它们仍保留身份、位置、质量、维护和历史。
- 总人口不是 `stock`，民用人力和可征募人力也不是可以储存、交易或凭空生成的资源。它们是人口对象按年龄、健康、地点、居留、资格和当前占用实时推导的容量视图；实际投入岗位的人数才进入各领域来源的 `activeCapacity` 或人员限制器。
- 科技完成、工程竣工、训练合格和维修恢复可以共用 `progress` 达标事件，但各自完成后生成的世界事实必须由对应领域处理。

## 11. 覆盖范围

本规格是 M1 及后续同类系统的月度数量计算唯一基线。`SPEC-M1-MONTHLY-RESOURCE-RESEARCH-SETTLEMENT-001` 只保存科研映射和科研数值，不再重复定义月度内核。

本规格不授权修改产品代码、数据、测试、构建或进入 `M0-L4-403`。
