# M0 层级、线程、记录与页面语言总规则

这是新第一层恢复时必须完整读取的规则总表。它不是摘要替代品；涉及具体语气和逐步纠错时，还必须读取任务卡指向的 session 原话。

## 1. 四层分别做什么

### 第一层：方向与总控

负责：

- 和用户讨论方向、玩法与系统；
- 把模糊想法整理成对象、条件、操作、资源、结果和验收；
- 决定任务应交第二、第三还是第四层；
- 创建或复用下层任务，登记并持续跟踪；
- 审查、退回、再次读取结果、独立验证；
- 维护方向规则、任务卡、session、路由、决定与 Git 收口。

不负责：

- 写故事成品；
- 写最终玩家文案；
- 修改游戏代码、样式、数据、资产、测试、构建或发布文件；
- 发现下层缺陷后亲自补一小段。

第一层可以只读代码和页面，也可以运行不改产品状态的验证。验证发现错误时，形成明确退回清单，发送给职责正确的下层任务。

### 第二层：故事与事件事实

只根据第一层冻结的系统事实组织人物、地点、触发、误解、变化、结果与恢复。它不增加资源、公式、地图规则或最终按钮文字。

### 第三层：玩家真正看见的文字

负责名称、按钮、状态、提示、通知、日志和完整正文。必须读取原始语料与用户原话，不能根据风格摘要仿写，也不能补写不存在的字段或世界事实。

### 第四层：实现与验证

负责代码、数据接线、样式、测试、构建和实际页面验证。只实现冻结规则和 accepted 字符串；遇到规则缺失返回 `BLOCKED_DECISION`，遇到正式文字缺失返回 `BLOCKED_TEXT`。

## 2. 实现前必须完成的线程派发

第一层必须按以下顺序工作：

1. 明确当前任务、输入提交、目标、非目标、文件白名单和验收。
2. 查找同一职责的安全旧任务。
3. 按复用规则复用，或按第四层大型批次规则建立新任务。
4. 在 `SESSION_ROUTING.md` 或 `ACTIVE_TASKS.md` 登记真实任务标题、Thread ID、Host、模型、思考深度、输入提交和状态。
5. 确认用户授权覆盖这张任务卡。
6. 向下层发送任务，让下层读取角色卡、任务卡、原话来源和冻结规格。
7. 登记完成前，任何产品文件都不得写入。

下层完成后，第一层必须主动等待或读取结果；侧边栏显示完成不等于结果自动回到主线程。

## 3. 创建失败、能力失败与上下文耗尽

### 创建动作失败

创建接口、项目归属、路由或任务对象生成本身失败时，同一次派发只新建一次。随后：

- 优先复用职责相符、状态安全的旧任务；
- 没有安全旧任务则返回 `BLOCKED_THREAD`；
- 第一层不能自己实施。

### 创建成功后能力失败

任务已成功建立，但模型无法完成、遗漏核心内容、错误反复或交付质量不足时：

1. 第一层记录具体失败证据；
2. 关闭失败实例；
3. 恢复干净工作区或保留清晰检查点；
4. 使用更适合的模型建立一个接替任务；
5. 接替任务沿用原任务范围，不能扩张。

这不属于“重复创建失败”。

### 上下文窗口耗尽

先把当前输入、完成内容、差异、验证、未完成项和下一动作写入 Git 检查点，再建立同层接替任务。不能用更长的提示把所有历史重新塞入新线程；应让新线程按路径读取权威原文。

## 4. 各层会话复用与模型

- 第一至第三层优先复用长期任务，保留方向、故事逻辑和文字风格。
- 第四层可按大型实施批次、上下文压力或能力不匹配定期新建。
- 同一稳定 lane 同一时刻只能有一个活动实例。
- 下层默认使用最低合理思考深度：机械工作 `low`，内容组织和边界清楚的实现 `medium`。
- 只有出现复杂架构、难复现根因、证据冲突或低档明确失败时才升 `high`，并记录原因。
- `xhigh`、`max`、`ultra` 必须由用户明确确认。
- 模型可随当时可用列表调整，但层级职责不变。

## 5. 第一层总控授权到底授权什么

用户此前给出的项目内持续授权，允许第一层不再为每个普通动作重复询问，可以管理线程、检查、退回、提交和推送。

它不允许：

- 第一层亲自写产品代码；
- 第一层代写故事或正式玩家文字；
- 越过一张执行单的白名单与阶段边界；
- 因线程慢、改动小或接近完成而取消分层。

只有用户针对当次任务明确说“允许第一层直接修改”，才形成一次性例外。例外必须记下原话、允许文件、目标和结束点；本次任务结束后自动失效。

## 6. 三种语言和四种状态

### 方向沟通用语

用于快速讨论想法，状态通常是 `discussion_only`。用户用了这个词，不表示页面也使用这个词。

本阶段已经明确的例子：

- `远期科技`：只是沟通中指科技路径后面的节点，页面只显示具体科技名称。
- `科技树`：当前只有两项科技，只能说路径或交互骨架，不能在验收记录中夸大为完整科技树。
- `一格`：可以指六边形机制单元，但不能在世界正文里当作距离单位。
- `工厂生产力`：可以用于计算；玩家页面优先显示投入几座工厂、每周期产量和原料。
- `标准工程包 v1`、内部 ID、存档版本、状态机、测试词、`系统会保留阻塞`：都不能进入玩家页面。

### 结构化界面字段

用于操作和判断，例如：资源名、库存、月度变化、岗位、进度、产品、工厂数量、开始按钮。字段要短，不写解释性小作文；能由布局、数字和按钮表达的内容，不再追加“系统会……”段落。

### 世界内正文

科技、工程、事件、通知和日志只写世界事实。它们不解释开发模型、不复述账本、不提示玩家应该注意什么，也不把机制词当文学语言。

### 四种文字身份

| 状态 | 含义 | 能否直接接入页面 |
|---|---|---|
| `discussion_only` | 沟通简称、类比、任务说明、内部字段 | 否 |
| `player_visible_provisional` | 界面位置已确定，用词尚未接受 | 只能做明确标记的原型，不能当成成品 |
| `player_visible_accepted` | 第三层成品或用户逐字接受 | 是 |
| `world_fact_only` | 可供故事和文字创作的事实 | 否，必须先经过第三层 |

没有标记的文字默认是 `discussion_only`。

## 7. 对话记录不能只剩摘要

以下情况必须保存关键用户原话：

- 用户连续多轮纠正同一设计；
- 用户指出某个词“只用于沟通，不能放页面”；
- 用户用具体例子校准语感、黑色幽默或故事逻辑；
- 用户否决某个候选，并说明为什么看不懂、出戏或逻辑不通；
- 用户只接受结构、不接受文字、视觉、内容量或最终品质。

记录必须包含：原话顺序、被否决内容、否决原因、修订方向、最后接受范围和仍未接受的部分。摘要可以帮助检索，但下层任务必须读取被指向的原话文件。

当前必读原话：`sessions/20260826-1900-mac-m0-s003-amendment-002.md` 的 U139 至 U143，以及 `sessions/20260826-mac-m0-s003-amendment-003.md` 的 U144。

## 8. 白天、夜间和大批次

- 白天优先由第一层和用户确定方向、范围、页面职责和验收，整合成一张任务单。
- 夜间由第四层执行一个边界明确的大结果，约六小时只是估算；工作完整且额度允许时可以八小时或更久。
- 结束前必须预留验证与交接时间。
- 夜间任务不能因时间充足自动跨入下一个正式阶段。

## 9. Git、状态与验收

- Git 是跨任务权威来源；代码、规则、状态和交接必须同提交、同推送。
- `proposal`、`user_confirmed`、`spec_frozen`、`dispatched`、`implemented`、`verified`、`accepted` 必须分开。
- 自动测试通过不是用户玩法验收；草图方向接受不是内容、美术和细节全部接受。
- 下层不得自己把任务标为 accepted，也不得自己启动下一阶段。
- 第一层没有读取实际下层结果、差异和验证证据时，不能仅凭“任务完成”推进。
